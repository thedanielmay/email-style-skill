# House email style

Files in this folder:
- `house_email.py`: every approved block as an inline-HTML function, plus `check()`, `to_text()` and `send()`. Build emails with it rather than hand-writing HTML.
- `templates.py`: the approved templates, one per email type plus the full picture sample. Run it to re-check them and regenerate `snippets.html`.
- `voice.md`: the content rules: the inputs each email type needs, sign-offs, tone by relationship, and how to write each purpose.
- `snippets.html`: the visual reference, generated by `templates.py`. Do not edit it by hand.

## Tiers

| Tier | Use when the content is | Allowed | Not used |
|---|---|---|---|
| **Full** | Technical: test results, prompts, code, A/B decisions | Everything below | |
| **Client** | For clients, funders or boards, or non-technical but substantial | Ask box, numbered headings, simple tables, pills, decision cards | Code, file names, prompt blocks, undefined technical words |
| **Light** | A short reply to anyone at work | A bold first line as the ask, then bullets | Boxes, headings, tables, subject tags |
| **Plain** | Family, friends, personal | `lines()`: one fact per line, no blank line between, and the occasional list | All other formatting, subject tags |

**One fact per line (Plain tier, set Thu 1 Oct 2026).** In a short multi-sentence paragraph, the second fact gets skimmed past. So each fact goes on its own line, with no blank line between the lines.
- A claim and its reason stay on one line: "We'll be late because the train is cancelled."
- Condolence and narrative writing stay as paragraphs (CLAUDE.md exemptions).

## Structure (Full and Client)

Each email follows this order. Drop any block that has nothing real to say.

1. Greeting: "Hi Name,". Contact shortcuts in CLAUDE.md override it, for example Leemo.
2. **One line of context**, for example "Following up on your Wed 30 Sep reply."
3. **Ask box**: `ask_box()`, exactly one per email.
   - **One thing to do:** `ask_rows(ask, by, unblocks, reply)`. The ask goes in bold, then the lines **By:**, **This unblocks:** and **Reply with:**.
   - **Several things to do:** `ask_steps([...])`, one numbered list. Each step may end with a `tag()`, for example "Releases Prompt 4" or "Can wait".
   - **Several recipients:** still one box. Each step starts with `<b>Name:</b>`.
   - **Never a second box.** Never a box nested inside the ask box.
4. Optional grey line under the box: `cc_line()` for Cc'd people (only when it is true), and `attached_note()`.
5. `since([...])`, the "Since my last email" box, in follow-ups when something changed.
6. Numbered sections: `h3("1. ...")`. Results tables go first, detail after.
7. Decisions:
   - A deadline table: Decision, Holds up, Needed by.
   - Then one `choice_card()` per decision.
   - Then the reply format.
8. Copy blocks (prompts, commands): `copy_block()`.
9. `attached_list()`.
10. Sign-off by situation (`voice.md`): "Thanks," for routine, "Much thanks," for a favour, name only after a complaint or boundary, "All best," for a warm note with nothing asked. Contact shortcuts override.

**No editorialised closer before the sign-off,** and no placeholder for one (CLAUDE.md Rules).

## Colour: each colour has one meaning

| Colour | Means, and only means |
|---|---|
| Yellow `#fff4cc`, `#e0a800` bar | The reader must act. Used for the ask box and for near-date cells only. |
| Navy `#1f3a5f` | Structure: headings, labels, copy-block bars, links |
| Pale blue `#f5f8fc` | Choices (decision cards) and set-aside context (the "since" box) |
| Green, red, grey, amber | PASS, FAIL, NOT TESTED, PARTIAL. Always pills with a symbol and a word, never colour alone. |

## Decisions

- **Card:** `choice_card(title, ul([A, B]))`, with each option starting with a bold "**A.** ...".
  - Use `table()` inside the card instead when the options change the same things, or the decision is complex.
- **Suggestion:** optional `suggestion("...")`, a grey "If you have no preference:" line under the options. Only Daniel's actual view, never invented.
- **How the reader replies:**

  | Situation | Reply format |
  |---|---|
  | One ask, or one decision | One sentence: "Reply with A or B." |
  | Two or more decisions, Full tier | `copy_line("Decision 1: __ Decision 2: __")` |
  | Client tier, or a reader new to this format | An example reply: "for example, 1A, 2B, 3 later" |

- **Questions with lettered choices (set Thu 1 Oct 2026).** In a numbered list of questions, stack the choices under the question with `options(stem, [choices], default=...)`, one per line, lettered A, B, C, so a reply like "3A" points at one.
  - Never run them inline ("A) ... B) ..."). In a line of text the letters get lost. `check()` warns on it.
  - A yes or no question stays inline and ends "Yes or no."
  - The default ("If I don't hear, A.") goes on its own line under the choices.
  - A question with no safe default (money, people, anything that can't be undone) gets `needs_answer=True`, the red tag, instead of a default.
- **Near dates:** a date within 5 working days gets `NEAR` cell styling and the day in words, for example "Tomorrow, Fri 2 Oct".

## Evidence

- **Status:** `pill()`, matched to the row.
  - A question gets `pill("YES", "PASS")` or `pill("NO", "FAIL")`.
  - A test gets `pill("PASS")` or `pill("FAIL")`.
  - Both use `pill("NOT TESTED")` and `pill("PARTIAL")`.
- **Code names:** `code()` chips, Full tier only.
- **Copy blocks:** `copy_block()`. When there are two or more prompts, also attach them as a file.
- **Links:** `link(text, href, where)`, which adds a grey "(Google Doc)" or "(GitHub)" after the link.
  - Every href must come from a real record, never typed from memory.
  - GitHub issues use `issue(repo, n)`, which follows the `repo#N` rule.
- **Screenshots:** inline with `figure(cid, alt, caption)`, passing `images={cid: path}` to `send()`.
  - No wider than the email.
  - The caption names what to look at.
  - Never a `data:` image, because Gmail blocks them.
- **Tables:** at most 3 columns. Anything wider becomes a list.

## Subject lines

New threads in the Full and Client tiers start with one of four tags:

| Tag | Pattern | Example |
|---|---|---|
| `[Decision needed]` | Project: what to decide | [Decision needed] SOFO Snapshot: three A or B choices |
| `[Action needed]` | Project: what to do | [Action needed] SOFO Snapshot: run prompts 1 to 3 |
| `[Question]` | The question itself | [Question] Should staging styles show before a publish? |
| `[FYI]` | Project: what happened | [FYI] SOFO Snapshot: date check passed |

- **Replies keep the thread's subject.** Changing it can split the thread in Gmail, so a new ask in a reply goes in the ask box.
- Light and Plain emails get no tag.

## Dates, times, numbers

- **"Fri 2 Oct" everywhere,** in sentences too: "your Wed 30 Sep reply".
  - Add the year only when it is not the current year, for example "Thu 1 Jan 2027".
- **24-hour times:** "14:00 to 14:30".
  - Add "Melbourne time" when the reader might be in another time zone.

## Length and size

- **Do not repeat in the email what the linked document already shows (set Thu 1 Oct 2026).** When the questions, changes or results already sit in a document the reader is linking to, beside the content they refer to, the email carries only the ask, the reply format and the link. A nine-question list pasted into the cover email was judged overwhelming when the same questions were already on page 1 of the linked deck.
- **More than about two phone screens of detail** goes into a Google Doc. The email keeps the ask and the link.
- **Gmail clips HTML above about 102KB** and hides the rest. `check()` blocks anything above 80KB.
  - The fix is to move the prompts to the attachment only.
- **Every send includes a plain-text part,** made by `to_text()`.

## Writing rules

Moved word for word from the global CLAUDE.md on Thu 1 Oct 2026. "Above" in this text refers to the shared writing-style principle and the plain-language rules in CLAUDE.md, which still apply. `check()` also warns on more than one bold phrase per paragraph or bullet.

**Default email sign-off (all emails, every project, set 2026-06-24):** `Thanks,` then `Daniel` on two separate lines. Use this unless Daniel specifies a different sign-off, or a contact shortcut defines its own (e.g. Leemo). This is the email default; the iMessage sign-off rule above stays "situational, no fixed default".

**Default email formatting (all emails, every project, set 2026-06-25):** Compose emails as HTML by default, not plain text. Follows the shared writing-style principle above (plain language, bulletize, never lose detail for brevity), plus these email-specific formatting rules:

- **Basic HTML emphasis for readability**: use `<strong>`/`<b>` for key terms, `<em>`/`<i>` where appropriate, plus headings and `<p>` breaks to aid scanning. Tasteful and functional, not decorative.
- **List item spacing**: put `style="margin-bottom:8px"` inline on every `<li>` (inline, not a `<style>` block; head styles get stripped by Outlook).
- These stack on the other email rules (sign-off above, no editorialised closer below, confirm before sending, no em/en dashes).

**Email writing rules, added 2026-09-30.** These seven came out of revising one client follow-up in September 2026, and they apply to every outgoing email, every project, from now on. They extend the shared writing-style principle above rather than replacing it.

1. **No mannered prose.** Style that draws attention to itself instead of to the subject, and shaping that makes Daniel the subject rather than the reader's task, both get cut. In practice this covers:
   - a not-X-but-Y frame where X is bad and Daniel lands on the good side, e.g. "a question for you rather than a guess from me"
   - a virtue signal, meaning a sentence whose real subject is Daniel's carefulness or thoroughness rather than the reader's job
   - defending a decision nobody has questioned
   - a claim about process with nothing to picture, e.g. "a figure is right" or "the release only goes out"
   - an aphorism, already banned under Display & Formatting
   - shaping picked for effect, where stripping the shaping costs no information
   - figurative substitution and cadence fragments, banned in full under Display & Formatting. A concrete-sounding image in place of a thing's name, the credit frame, and two-word fragments like "Nothing to read" are all cut, in email as everywhere else

   Two questions to ask before cutting anything:
   - **What does this do for the reader?** If the answer is "it shows I am careful" or "it sounds good", cut it and say the thing the reader needs instead.
   - **Is the subject the work, or Daniel?** Warmth pointed at the reader is fine, and shaping that carries information forward is fine. Shaping that substitutes for information is not.

   Guard against over-applying it: "so I would love to hear how it went" is shaped, and it stays. Its subject is the reader, and it asks them something. If Daniel wants the check run on a draft, the short prompts that work are "is any of this mannered, or about me rather than her?" and "what does this do for her?"

2. **Non-negative phrasing (all emails, every project, set 2026-09-30).** Never let the negative reading land last in an outgoing email. Blocking facts still get stated plainly, but the framing carries the news in positive or at least non-negative form. Promoted from the Green Collect project file, where it was Laura's March 2026 note, so it is now global rather than project-specific.

3. **Hedge the recall, not the sentence (set 2026-09-30).** When a date or fact comes from memory rather than from a record, mark the recall: "I think the Social Traders meeting was on 21 or 22 September". The corollary matters as much: do not hedge what is actually documented.

4. **Offer the recipient's lowest-friction format, never Daniel's preferred one (set 2026-09-30).** If the work can be done in writing, do not propose a call. Offer the formats the recipient already uses, say any order is fine, and say what happens as each piece lands so there is visible progress. Do not assert a form the recipient has not been seen to use, such as offering voice memos without checking that is genuinely how they work.

5. **Show the draft rendered, never as raw HTML (set 2026-09-30).** For review, display the email as the recipient will see it, with the To, Cc and Subject headers, and do not paste markup. The HTML is for the send step only.

6. **Reply in-thread for any follow-up (set 2026-09-30).** A follow-up on prior correspondence goes out as a reply, so the subject line and the history survive. Never open a fresh email to re-raise something already under discussion.

7. **More bullets, straight language, no dilution, unmissable ask, format for density (set 2026-09-30).** A bundle, and each part earns its place.
   - **Bulletise wherever the content allows.** One claim per bullet, nesting rather than compressing, as above.
   - **Straight, plain words.** Prefer the shorter Anglo-Saxon word where it is exact, as above.
   - **Succinct never means withheld.** When Daniel asks for shorter, cut length, not content. Every fact, qualifier, number, date and exception stays unless he removed it. If something has to leave to make the email shorter, it goes to the review notes as a flagged decision, never silently into the bin. This does not block shortening, it only means removals are surfaced and Daniel decides.
   - **The ask is unmissable.** One call to action per email, stated as a specific action by the reader, placed where it cannot be skimmed past. If a warmer closer would help, it carries the ask rather than replacing it.
   - **Use formatting on dense content, do not hold it back.** Bullets and sub-bullets, headings, a table when the content is comparison-shaped, a numbered list when it is sequential, bold on the one or two terms carrying the meaning. Formatting stays functional rather than decorative, as above, and density is the trigger to use more of it, not less.

## Full picture formatting (only when Daniel asks)

**Trigger words (set Fri 6 Nov 2026):** "full picture", "full picture formatting", "full picture style". Never the default, never applied unasked. Daniel chose "full picture" for its wide view feeling: everything is laid out at once so the reader sees the whole picture.

**What it is:** a self-contained presentation in which the short answer comes first, the proof sits in fit tables, and the reader can follow the options, questions, decisions and timeline without opening a Doc. It is the longest house style. It suits a reader who wants the whole picture in one email, such as the Downer advice email to Kathy Sun, Fri 6 Nov 2026.

**Layout, built with the blocks in `house_email.py`:**

- 760px max width, house font and ink, navy for structure, pale blue for the Short answer box, yellow for the one ask box.
- Greeting, then one line of context, for example "Replying to your Wed 4 Nov email about the Downer roles."
- The one ask box, with By, This unblocks, and Reply with lines, when the reader must act. When no action is needed, drop the ask box and state the next steps in the Short answer box instead.
- The Short answer box first (pale blue, navy left bar). Each verdict is a bold lead phrase plus one reason, for example "Apply for the Subcontractor Support Officer first." Then a second yellow box, "Your next steps", with a numbered list and a date pill for each step, for example "By Tue 10 Nov".
- Numbered sections with a navy heading and thin underline, for example "1. The three roles". Results and comparisons come first, detail follows.
- Fit tables with at most three columns and a fit column at the right. Each cell uses `pill()` with a symbol and a word, for example BEST FIT, SECOND OPTION, ASK ONE QUESTION, STRONG, GOOD, PARTIAL.
- Term callouts for definitions, in the same pale blue box with a navy left bar, for example "What SDP means".
- One quoted question in a callout when a single question decides the next step, for example "What share of the Scheduler's day is phone calls?"
- If and then tables for contingent advice, such as "If the answer is mostly phone, leave the Scheduler role".
- Lettered questions with stacked choices from `options()`, so a reply like "3A" points at one answer.
- Decision cards with a reply example or a `copy_line("Decision 1: __ Decision 2: __")` line when the reader must choose.
- A timeline table at the end with date plus steps, then the house sign-off.

**Why it stays long:** a full picture email keeps the proof, the questions, the decisions and the timeline in the email itself, rather than moving them to a linked Doc. That is the point of the style. `check()` still blocks HTML over 80KB, so when the email would exceed that limit, move the longest detail to an attachment and keep the full picture shape around it.

**Guardrails:**

1. **The short answer must be true on its own.** A reader who reads only the Short answer box and the next steps box should know what is advised, what to do next, and by when.
2. **Do not invent a verdict.** Say "not decided yet" when a question decides it, and name that question in the next section.
3. **Keep one ask.** When the email has both a CTA and decisions, use one ask box for the reply, then decision cards for the choices. Never a second ask box.
4. **Fit must match the row.** Use `pill("YES", "PASS")` or `pill("NO", "FAIL")` for a question, `pill("PASS")` or `pill("FAIL")` for a test, and `pill("NOT TESTED")` or `pill("PARTIAL")` where neither applies. Never colour alone.
5. **Say it in the preview.** Write "Full picture" beside the tier and name any inbox content that was moved to an attachment.

## Telegraphic style (only when Daniel asks)

**Trigger words (set Fri 6 Nov 2026):** "telegraphic", "telegraphic style", "telegraphese", "telegram style". Never the default, never applied unasked. Daniel chose "telegraphic" over his earlier word "clip it" on Fri 6 Nov 2026 because it is more specific.

**The terms:** the plain name is *telegraphic style* (telegraphese). Related: headlinese (the newspaper version, which also uses "to" plus a verb for the future), cablese (press messages over undersea cables), and ellipsis (the grammar term for leaving out words the reader can supply).

**What it is:** cut the small words so only the information-carrying words stay. The email still reads clearly though it is not grammatically complete. Example: "I will get the form ready for option A in the meantime" becomes "We'll get form ready for option A in meantime."

**Rule 0: cut words, never facts.** This is writing rule 7 above (succinct never means withheld). Every number, date, time, amount, name, deadline, condition, negation and exception survives.

Cut these:
- articles (a, an, the) where the sentence stays clear
- contractions ("we'll", "it's", "don't")
- "I will" and "I am" become "we'll" and "we're" when Daniel speaks for the working group (his example). Keep "I" where only Daniel acts.
- filler and softeners (very, really, in order to, a bit)
- "to be" in lists, table cells and headings

Never cut these:
- negations: not, no, never, none, nothing, without, n't. Dropping one reverses the meaning.
- qualifiers: only, may, might, probably, if, unless, except, about, up to, at least. They are the first thing over-cutting loses, and losing one can make a claim false.
- numbers, dates ("Fri 6 Nov"), times, amounts and names. A body's full name stays on first mention ("Essendon Baptist Community Ministries Inc (EBCM Inc)").
- who does what in any ask: the actor stays clear in every step
- the greeting, sign-off, ask-box labels (What I need from you, By, This unblocks, Reply with), headings and option letters
- the house rules: no dashes, one ask box, no closing line

**Guardrails:**
1. **Full version first.** Write and approve the full email, then write a telegraphic copy. Keep the full one beside the draft so Daniel can compare and nothing is lost.
2. **Run `facts_kept(full_html, telegraphic_html)`** (in `house_email.py`). It must return an empty list. It catches dropped numbers, dates, amounts, names, acronyms, and negation and qualifier words. It cannot see a changed meaning or a lost actor, so also read the two versions side by side. A flag is a prompt to check, not a failure: a word you cut on purpose will show up (for example a cell that opened with "Closest"), so decide each one. Names at the start of a table cell or list item are the usual false alarms.
3. **Restore anything that reads two ways.** If dropping an article or pronoun makes a sentence ambiguous, or needs a second read, put the word back. Test: read it aloud once, and restore any sentence you stumble on.
4. **No cadence fragments.** A telegraphic fragment must carry a fact ("Real deadline is 17:00 Fri 13 Nov."). A fragment kept only for rhythm ("Not before.") is cut, per the cadence-fragment rule in CLAUDE.md.
5. **Reader test.** Telegraphic style suits readers who share the context (Adam, with the Doc open). To strangers, funders, officials, boards, or in a complaint it reads curt: say so in the review notes and ask Daniel before using it.
6. **Never use it for:** condolence, pastoral or narrative writing, grant answers and other assessor-scored prose, policy or legal clause text (the CLAUDE.md exemptions), and iMessage.
7. **Say it in the preview.** Write "Telegraphic" beside the tier, and list in the review notes anything cut that carried even slight meaning.
8. Then run `check()` as usual. It still blocks dashes, a second ask box and the rest.

**Why the limit exists:** telegraphese began as a way to pay for fewer words on telegrams (Wikipedia, "Telegram style"). Language Log's point is that the little words carry cues to meaning and intent, so over-cutting confuses readers. First used on the Brighton St email to Adam, Fri 6 Nov 2026.

## Checks that `send()` runs (`check()`)

**These block the send:**
- an en or em dash
- a `<style>` tag or `class=`
- a `data:` image
- HTML over 80KB
- a table with more than 3 columns
- more than one ask box

**These warn but still send:**
- run-on lettered options ("A) ... B) ...") in one paragraph or bullet; use `options()`
- more than one `<strong>` in a paragraph or bullet
- a bare `#N` issue reference

After changing any block, run `python3 templates.py`. It re-checks every template, tests that the checker still catches what it claims to, and regenerates `snippets.html`.

**Telegraphic guard (not run by `send()`):** `facts_kept(full_html, telegraphic_html)` returns what the full version had and the telegraphic one lost (numbers, dates, amounts, names, acronyms, and negation and qualifier words by count). An empty list means nothing detectable was lost. Run it by hand on every telegraphic email.
